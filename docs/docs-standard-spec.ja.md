# ドキュメント標準仕様

> **目的**: 本書は、VitePress（SSG）と Sphinx（Python API リファレンス）を使用した
> ドキュメントサイト構築の標準仕様を定義するものです。人間と AI エージェントの
> 双方が理解・保守できるよう構造化されています。
>
> **技術スタック**:
>
> - **サイト生成**: VitePress (Node.js)
> - **API リファレンス**: Sphinx (Python) + `sphinx-markdown-builder`
> - **設定**: `pyproject.toml` (Python), `package.json` (Node.js)

## Diátaxis フレームワーク概要

本標準では、ユーザーの即時のニーズに基づき、ドキュメントを 4 つの種類に分類します。

| **種類**       | **指向**   | **役割**                                                         | **例え**                     |
| -------------- | ---------- | ---------------------------------------------------------------- | ---------------------------- |
| **チュートリアル** | 学習       | 著者の指導のもと、演習を通じてスキルを習得する。                 | 子どもに料理を教える         |
| **ハウツーガイド** | 目標       | 具体的で実践的なタスクを完了するための手順。                     | 料理本のレシピ               |
| **リファレンス**   | 情報       | 技術的事実の正確で簡潔な記述。                                   | 栄養成分表示                 |
| **解説**           | 理解       | 背景、設計根拠、議論を通じて理解を深める。                       | 料理史に関する記事           |

## ドキュメントの 5 原則

1. **読者第一**: 各ページの対象読者を明確にする。初心者向けの「教育」と
   専門家向けの「事実」を混在させない。
2. **段階的開示**: L1（ホーム）→ L2（はじめに）→ L3（チュートリアル/ハウツー）
   → L4（リファレンス）の順に情報を階層化する。
3. **サンプル駆動**: コードサンプルは、環境構築済みの前提で、そのままコピー＆
   ペーストで実行可能であること。
4. **唯一の情報源**: API リファレンスはソースコードの docstring から自動生成する。
   手書きドキュメントは「なぜ」（根拠）と「どのように」（手順）に使用する。
5. **AI/LLM フレンドリー**: 構造化された見出し、テーブル、メタデータを使用し、
   AI エージェントが正確にコンテキストを解析できるようにする。

## Diátaxis とサイト構造の対応

| **サイトセクション** | **主な Diátaxis タイプ** | **内容**                                                                 |
| -------------------- | ------------------------ | ------------------------------------------------------------------------ |
| **ホーム**           | N/A                      | キャッチコピー、最小限のコード例                                         |
| **はじめに**         | 混合（タグ付き）         | インストール（ハウツー）、クイックスタート（チュートリアル）、アーキテクチャ（解説） |
| **チュートリアル**   | チュートリアル           | 主要ワークフロー別に整理された学習レッスン                               |
| **ハウツーガイド**   | ハウツー                 | 特定タスクの手順（例：「認証の設定方法」）                               |
| **リファレンス**     | リファレンス             | Sphinx 生成の API ドキュメント、用語集、設定一覧                         |
| **解説**             | 解説                     | 設計判断、アーキテクチャの詳細解説、経緯                                 |

## ディレクトリ構造

```text
.
├── docs/                 # VitePress ソース
│   ├── index.md          # ホームページ
│   ├── getting-started/  # オンボーディング（インストール、基本概念）
│   ├── tutorial/         # チュートリアル
│   ├── how-to/           # ハウツーガイド
│   ├── explanation/      # 解説
│   └── reference/
│       ├── index.md      # リファレンス概要
│       └── api/          # Sphinx から同期された Markdown
├── sphinx/               # Sphinx 設定 (conf.py, index.rst)
├── scripts/              # 同期スクリプト (build-docs.sh)
├── pyproject.toml        # Python 依存関係 (Sphinx, napoleon 等)
└── package.json          # Node.js 依存関係 (VitePress)
```

## ツールチェーン設定

### Sphinx (Python)

- **スタイル**: `napoleon` を使用して Google スタイルの docstring を記述する。
- **型ヒント**: `autodoc_typehints = "description"` に設定する。
- **出力**: `sphinx-markdown-builder` を使用して VitePress 用の Markdown を生成する。

### VitePress (Node.js)

- **サイドバー**: Diátaxis のカテゴリに従ってグループ化する。
- **リンク**: 内部相互参照には常に相対パス（`[Link](../how-to/page.md)`）を使用する。

## 種類別の執筆手順

### チュートリアルの書き方

1. 1 つのワークフローに焦点を当て、他と混在させない。
2. 一人称複数形（「～しましょう」）を使用してユーザーを誘導する
   （例：「API に接続しましょう」）。
3. 重要なステップごとに「期待される出力」を記載する。
4. 説明は最小限にとどめ、より深い文脈が必要な場合は「解説」ページにリンクする。

### ハウツーガイドの書き方

1. タイトルは「～の方法」で始める。
2. 命令形を使用する（例：「認証情報を設定する」）。
3. 読者の能力を前提とし、基本概念の説明は省略する。
4. 条件分岐を明確に記述する（例：「X の場合は Y を行う」）。

### 解説の書き方

1. タイトルは「～について」または「～の解説」で始める。
2. 背景、設計上のトレードオフ、代替案との比較を記述する。
3. ステップバイステップの手順や API パラメータ一覧は含めない。

## API 変更時のメンテナンスフロー

API が変更された場合、以下のチェックリストを実行する：

1. **Docstring の更新**: パラメータ、型、説明の変更をコードに反映する。
2. **自動生成の実行**: `scripts/build-docs.sh` を実行して
   `docs/reference/api/` を更新する。
3. **関連ドキュメントの改訂**:
   - `リファレンス`: サマリーテーブルを更新する。
   - `ハウツー`: 更新された API を使用する手順を修正する。
   - `変更履歴`: 変更内容を記録する。
4. **相互参照の検証**: リンク切れを確認する。
